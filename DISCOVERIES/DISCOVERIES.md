# Methodology Discoveries

This log preserves observations from design practice. An observation may later inform a method principle, but being recorded here does not make it a validated Human Truth.

A product keeps its own discoveries in the folder it copied from `STARTER_KIT/DISCOVERIES/`. This file is the methodology log. The list below stays here.

An entry names a realization and its consequence for design. For example, the observation that emotional reconnection can precede information processing changed how Recognition was designed. This is an illustration of the log format, not an additional registry entry.

## DISC-006
A Refusal Needs a Positive Still Object
HTDD made Reflection implementable by naming the failure mode in advance: the danger was not missing features, it was designed silence that still read as a product gap. The useful refinement is that restraint copy is itself Product Gravity, and a refusal needs a positive still object or it looks unfinished.

## DISC-007
Refusals Do Not Prove Readiness
HTDD is unusually strong at telling a team what not to build, but it is still less complete at telling a prototype when an emotional moment is ready. Refusal patterns can prevent the wrong product; they do not by themselves prove the right emotional experience. Observed, not doctrine.

## DISC-008
Define Source, Then Only Carry It
HTDD earned its keep when “representative content” stopped meaning “invent a believable person” and started meaning “publish a tiny source kit, then refuse to speak beyond it.” Observed, not a new Human Truth.

## DISC-009
A Merged Ticket Is Not Acceptance
HTDD kept emotional intent, safety boundaries, implementation, and validation connected across a long milestone. It also left implementation tickets open after the code had merged, because human gates were attached before that class of work was finished. Specification, implementation, automated verification, human validation, and acceptance are different events. Automated checks can establish behavior and guardrails. They are not approval by a named human reviewer, including the Arc Steward. A build is ready for participants when the end-to-end product journey can be walked. Observed from one product milestone, not doctrine.

## DISC-010
The Finish Line Stays Small
A later phase confirms an exclusion, a defect stays inside the current shell, and a ticket names the next slice it will not absorb. The path still open after a merged journey is evidence and named review. Adding product so the work feels finished starts the backlog again. Observed from one product, not doctrine.

## DISC-011
The Governing Milestone Must Still Bind
A milestone does not govern until its summary restates the exclusions that still bind, or names the predecessor file that holds them. An agent file that names a milestone folder, or tells an agent to sort the milestone directory, is stale when the current pointer is missing or names a different folder. A quality pass cannot add a surface, a collection, an access path, an invitation channel, or a discovery query. Code that disagrees with the governing contract is not done. A ticket is not implemented while a test that locks its contract is red. Observed from one product, not doctrine.
